Git Branching: Work Without Disturbing the Main Code
Branching in Git lets you create a separate path from the main project, allowing independent work without affecting the original code.

How It Works

. A branch is like a snapshot of the main project at that moment.
. You can freely modify, test, and update the branch without impacting the main code.
. Once everything is tested and ready, you merge the branch back to the main.

Why Use Branching?
. Develop new features without breaking the main code.
. Fix bugs safely before applying changes to the main branch.
. Enable collaboration so multiple developers can work simultaneously.
. Test thoroughly before making changes live.
. Keep the main branch clean for production use.
. Provides a clear history of contributions. You can easily see who worked on what and
when, which makes tracking and managing the project very easy.

Git Branching Flow: From Main to Production
This flow helps manage code safely from development to deployment.

1. main/master is the main production code
. This branch holds the live and stable code that is already deployed to users.
. We never directly work on this - only tested and approved code goes here.

2. Create development branch from main
. This becomes the working branch where all ongoing updates and new features are merged.

3. Developers create feature branches from development
. Every new feature is built in a separate branch (like feature-login, feature-payment).
This keeps each developer's work isolated.

4. After completion and testing, feature branches are merged into development
. Only after unit testing or code review, features are added back to development.

5. QA team tests the development code in a QA or STG environment
. All integrated features are tested together to check for bugs or issues.

6. Once QA is approved, changes are moved to UAT (User Acceptance Testing)
. Final testing happens here with the business team or client.

7. After UAT success, merge development into main and deploy to production
. Now, the tested code reaches the live environment for users.

Why This Flow is Good
. Keeps production code safe
. Allows parallel feature development
. Enables multiple testing layers (Dev - QA -+ UAT)
. Reduces risk of bugs reaching production

Handling Hotfixes in Git Branching
Hotfix branches are crucial when an urgent issue needs fixing in production without disrupting
ongoing development.

Hotfix Workflow

1. Create a hotfix branch from main/master
. Example: hotfix/security-update, hotfix/payment-bug.
. This ensures the emergency fix is applied directly to live code.

2. Apply and test the fix in the hotfix branch
. Validate the fix before deploying quick but thorough testing is key.

3. Merge the hotfix into main/master and deploy
. Once confirmed, merge the hotfix branch directly into main/master for immediate release.

4. Backport the fix to development
Merge the hotfix branch into development to ensure the fix isn't lost in future releases.

Why Merge Hotfix to Development After Merging to Main?
Yes, you first merge the hotfix to main to fix the issue in production. But then, you also need
to merge it into development - here's why:
You have two branches:
. main -> Live code in production
. development -> Ongoing feature work
Now suppose you fixed a bug in a hotfix branch and merged it into main.
But ,If you don't merge it into development, the fix will be missing when the next feature release
goes from development -> main.
1. Git Branch Commands
In Git, the git branch command helps us do many things like:
. List all branches
. Create branch
. Delete a branch
. Rename a branch
. Switch from one branch to another
1. List Branches
git branch
This shows all local branches.
. The one with * is your current branch (means you're standing on that branch now).

2. Create a New Branch
git branch dev
git branch < name >
This creates a new branch called dev based on the branch you're currently in.
. But you will still stay in your old branch.

3. Switch to Another Branch
We switch to another branch when we want to start working in that branch.
Old Way (Still Works)
git checkout dev
git checkout master
. This moves you into the dev and master branches.

New Way (Git version 2.23+)
git switch is a modern alternative to git checkout
Git introduced a simpler and safer command in version 2.23 and above called git switch.
git switch dev
git switch master
. Same as above, just a newer and clearer command.
. It's better to use git switch because it is specially made for branch switching only.

4. Create and Switch to a New Branch
If you want to create a new branch and move into it in one shot:
Old Way:
git checkout -b feature-1

The command git checkout -b feature-1 is used to create and switch to a new branch
called feature-1.
New Way (Recommended):
git switch is a modern alternative to git checkout that does the same thing creates and
switches to a new branch.
git switch -c feature-2

Here, -c means "create and switch"

. git switch is used only for branch operations
. git checkout is used for both branches and file operations
. So git switch is safer and easier when working with branches

5. Rename a Branch
You can rename a Git branch at any time, whether it's a local branch or a remote one.
git branch -m < old-name > < new-name >
. If you're not on the branch you want to rename:
This renames dev to development.
. If you're already inside the branch, just use:
git branch -m new-name

6. Delete a Branch
You want to delete a branch after work is done:
git branch -d feature-2
. You can also delete multiple branches at once like this:
If Git says it's not merged and still you want to delete:
git branch -D feature
Note: You cannot delete the branch you're currently on. First switch to another branch, then
delete.

4. What Happens If You Don't Commit Before Switching
Branches?
. You're on the development branch and you edited a file (Demo. java) like this:
// old line
Adding new feature = 3
// You changed it to:
Adding new feature = 4
. But you didn't save or commit the file, so the status shows it is still not committed.
Now You Run:
git switch master
You'll see: Adding new feature = 4
M Demo. java
. M stands for Modified.
. This tells you that Demo. java has uncommitted changes.
. And Git carried those changes into the master branch when you switched.
. Even though you never committed it in development, it came with you to master.
. This is exactly what we call "auto-carrying" Git moved the changes with you silently
because:
. There were no conflicts in master
. This is called auto-carrying it can accidentally leak code into other branches, which
is dangerous in real-time teams
Tip: Avoid Auto-Merge Accidents
. Never switch branches with unsaved/uncommitted edits.
· Always:
. git commit the changes, or
. git stash to save them temporarily

5. What is a Merge Conflict?
Let's say we have:
. A master branch (main code)
. A development branch (you are working here)
. A feature branch (your teammate is working here)
You and your teammate both edit the same file (Demo. java) and even the same line, but with
different content.
1. In development, you add:
Adding new feature = 5
. Switch to development and modify the file:
. Edit Demo. java and change this line:
Now stage and commit:
git add
git commit -m "Updated 5 in Demo. java"
2. In feature, your teammate added:
Adding new feature = 10
. Switch to the feature branch
. Edit Demo. java and change the same line to.
. Now stage and commit:
git commit -am "Updated to 10 "
3. Merge feature into development
Now switch back to development and try to merge feature into it:
git switch development
git merge feature
. Git will stop and say: Merge conflict in Demo.java
. Now if you try to merge feature into dev, Git doesn't know which line to keep.

4. Resolve the Conflict
. Open Demo. java, and you'll see something like:
These lines are called conflict markers:
. <<<<<<< HEAD-> this is the change from your current branch (development)
- this separates the two conflicting changes
. >>>>>>> feature -> this is the change from the branch you're merging (feature)
. You need to edit this file manually, choose what to keep then save it.
. This is called a merge conflict.
. After editing and saving Demo. java, you need to stage and commit the changes.
git commit -am "Resolved merge conflict in Demo.java"
Note: No Need to Merge Again
. After resolving the conflict and committing the merge, you can check the same line in both
branches and you'll find the same content in both.

1. What is a Git Tag?
A Git tag is like a version sticker for your code it marks a specific point in your project's
history, usually after a stable release.
Tag = Version
"A tag is nothing but a version label (like v1.0.0) that you give to the current clean and tested
code on your main branch."

What Git Tags Help You Do:
. Mark stable versions of your project (like v1.0.0, v2.1.0)
. Refer back to a specific version anytime in the future
. Use in deployments CI/CD pipelines can deploy based on tags
. Make your code downloadable from platforms like GitHub (as .zip or .tar)
. Rollback easily if something goes wrong in future versions, you can jump back to the tagged
version instantly

2. Git Workflow with Tags
Here's how versioning typically works in a structured Git workflow especially in real-time team
environments like IT projects :
1. Feature Development
. A developer creates a feature branch from the development branch.
. They work on new features or bug fixes.
. They perform unit testing, code review, etc.
. If everything is working fine, it goes to the next stage.
2. Testing Stages - STG & UAT
. After unit testing, the feature goes through:
. STG (Staging) - Internal testing
. UAT (User Acceptance Testing) - Client validation
. Bugs, if any, are fixed and re-tested.
3. Merge to Development
. Once the feature passes STG and UAT, it is merged into the development branch.
4. Merge to Main
. The development branch is tested again.
. If the code is stable, it is merged into the main branch.
. If any issue occurs, they roll back instead of merging.
5. Version Tagging
. Once the code in the main branch is clean and stable, a Git tag is created.
. The tag represents the version of the current code, e.g., v1.0.0.
. This tag becomes a reference point for production deployment.

3. Example: Tagging a Shopping App Release
Let's say you're working on a Shopping App with key features like login, cart, and payment.
Development Process
1. You build each feature on separate branches 2.You perform: Unit Testing ,STG (Staging) Testing
,UAT (User Acceptance Testing) . 3. After all testing passes, the code is merged into
the main branch
Now the main branch is stable
It contains clean, tested, production-ready code.
Create a Tag to Mark This Version
To lock this state in Git history, use:

git tag ShoppingApp_v1.0.0
git push origin ShoppingApp_v1.0.0


What does this mean?
"This is version 1.0.0 of our Shopping App - stable and tested. We're tagging this point to
lock it as a reference for future use."
Now this version:
. Is downloadable as ZIP/TAR from GitHub
. Can be restored any time using the tag
. Can be used to trace what went into that release

4. Types of Git Tags - Semantic Versioning
In Git, tags often follow a concept called Semantic Versioning, which helps you identify the
purpose and impact of a release at a glance. The format used is:
< major > .< minor > .< patch >

For example: v2.4.1 Explanation:
. Major version changes indicate big updates that may break backward compatibility.
For example, changing from 1.0.0 to 2.0.0 means some old features might not work anymore.
. Minor version changes mean new features have been added, but the update is
still backward-compatible.
For example, moving from 1.1.0 to 1.2.0.
. Patch version changes are for bug fixes or small improvements that don't affect the feature
set.
For example, 1.1.1 to 1.1.2.

8. What is Git Stash?
You are working on a feature in the development branch. Suddenly, an urgent issue comes in master.
You can't commit half-done work. What do you do?
. Here you are working on the file Demo. java. You exited the file, and now it shows as modified.
Use git stash - it hides your changes temporarily.
git stash list helps you see the files in the stash list.

1. Save Your Work with Git Stash
This saves all uncommitted changes (tracked files only) and provides you with a clean working
directory.
git stash save "payment integration – 2025-06-15 13:20"
This command saves your current changes into Git's stash, allowing you to temporarily store
unfinished work without committing it.
Using a timestamp in your stash message is a great practice.
. git stash - Temporarily stores your uncommitted changes.
. save "payment integration - 2025-06-15 13:20" -> Provides a label for the stash so you can
easily reference it later.
. After using the stash, running git status will show a clean working tree. This means it won't
automatically merge.
2. Switch to Master and Fix the Issue
git switch master
Make the required fix and commit.
3. Go Back to Dev and Apply the Stashed Work
git stash list
git stash apply stash@{o}
. After applying the stash, your working tree changes from clean to modified.
. Now you can edit the files, stage them, and commit your updates as needed.
4. Drop the Stash (Delete it)
git stash drop stash@{o}
. Deletes the specific stash entry stash@{o} from your stash list.
. You no longer need that stash and want to clean up space.
Note: It only deletes the selected stash, not all.
Or if you want to clear all:
git stash clear
This removes all stashed changes from your repository, clearing out the entire stash list.
. git stash -> Manages saved changes.
. clear - Deletes all stashed entries (unrecoverable).
git stash pop
git stash pop applies the stash and then deletes it from the stash list.

This command:
. Applies the latest stash (stash@{0} - shell updating)
. Removes it from the stash list after applying
. The output shows the def. sh file was restored (modified)
. Which confirms that stash was popped (applied and deleted).
Check stash list again:
. Now, only one stash remains:
· stash@{o}-"payment new updating"
(Note: the index gets renumbered. What was stash@{1} before is now stash@{ø}.)
. Unlike git stash apply, which restores the stash but keeps it in the list, git stash pop applies
the stash and removes it immediately.
